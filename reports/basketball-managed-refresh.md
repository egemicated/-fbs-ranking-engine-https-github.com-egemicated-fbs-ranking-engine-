# Basketball production refresh

The candidate workflow uses the existing GitHub Actions and Render release path. Basketball status, records, advanced team and player inputs, the independent rankings, saved forecasts, results, and report-card grading travel together as one candidate. A failed provider call or failed release check leaves the prior site available. Football keeps its existing refresh timing and publication workflow.

## Schedule and freshness

Times are Mountain Time. The basketball scheduler uses `America/Denver`, so the local hour stays fixed when UTC offsets change. GitHub may delay or drop a scheduled run. The backup uses the nominal schedule date and the encrypted primary outcome. [GitHub schedule behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

Finals need validated scores and matching season/game/team identities. A confirmed tipoff is considered elapsed after 160 minutes. Overtime, delayed updates, other timezone differences, and missing records prevent that threshold from guaranteeing a final. The rolling check can incorporate scores, status, team boxes, and player statistics that arrive later. Public pages preserve their actual snapshot time. Content and prospective forecast changes determine whether a new build is needed. Replays never become live forecasts.

## Monthly planning estimate

These are scheduling assumptions, with retries and postponed/missing game traffic variable. The limits below apply before any individual request is allowed.

| Profile | Football calls | Basketball calls | Combined planning range |
| --- | ---: | ---: | ---: |
| Football regular season without basketball | 65–125 | 0 | 65–125 |
| Basketball-only regular season | 0–15 | 95–155 | 95–170 |
| Overlapping regular seasons | 65–125 | 95–155 | 160–280 |
| Football postseason overlapping basketball | 10–65 | 95–155 | 105–220 |
| Conference and NCAA tournaments | 0–15 | 100–200 | 100–215 |
| Offseason | 0–15 | 0 | 0–15 |

Basketball estimates account for the approximate 3–5 call nightly batch and weekly metadata inside the high end. The March–April range includes selective evening checks and corrections. A busy day may split into more windows when an endpoint reaches its record cap. A roster/bootstrap/research acquisition is excluded from steady-state estimates.

The provider advertises one 1,000-call allowance across football and basketball for the free tier. The production runner reads both authenticated, non-metered `/info` endpoints and requires matching tier, UTC reset and remaining balance before proceeding. A separate basketball credential requires verified linkage to the production football account in addition to matching readings. The runner will never switch credentials to continue spending. It retains a 600-call football reserve plus 150 calls for contingencies, caps basketball at 250 tracked attempts per provider reset, and holds each scheduled run to 12 reserved attempts including retries. It also counts an attempt before sending it. The reserves are deliberately conservative. Heavy football or research use can pause basketball even if the planning range suggests enough combined calls. Different credentials may have unrelated balances, and a response containing `sharedPool: true` alone does not prove they are linked. [CBBD quota endpoint](https://api.collegebasketballdata.com/api/info) · [CFBD quota endpoint](https://api.collegefootballdata.com/api/info) · [Provider terms](https://collegebasketballdata.com/terms)

No cross-sport distributed lock was added to the existing football jobs. The authenticated balance observation, large reserve, serial basketball workflow, and per-request provider accounting limit exposure when football and basketball overlap. The GitHub job summary intentionally omits the exact balance and failures containing private source context because the repository is public. The encrypted state retains the observed balance, attempts, missing-game IDs, and recent recorded checks. From a protected computer, `node scripts/run-basketball-refresh.mjs --mode inspect --input <sealed-file>` shows the retained balance and latest check without printing underlying source records.

## First activation and rollback

1. Complete the release gate and confirm the main football credential has authorized basketball access on the same allowance. If a separate platform key is needed, verify the linkage with the provider before furnishing it through the private repository secret and setting `BASKETBALL_SHARED_ACCOUNT_VERIFIED`. Leave the working football secret untouched.
2. Generate a random 32-byte key and provide its lowercase hexadecimal form through the secure environment as `BASKETBALL_REFRESH_CACHE_KEY`. With the approved source and immutable forecast/edition files in this worktree, run `node scripts/run-basketball-refresh.mjs --mode pack --output research/cache/basketball/managed-refresh.encrypted.json`. The packer runs offline. Keep a verified copy in existing owner-controlled private storage, including updated working backups as part of operations.
3. Supply a short-lived private HTTPS link for that encrypted file through the repository’s `BASKETBALL_REFRESH_SEED_URL` secret. The runner does not accept redirects and authenticates the contents before restoring data. Enable `BASKETBALL_REFRESH_ENABLED` and dispatch `seed` from main during the approved rollout. The seed dispatch spends zero sports calls and leaves the public site untouched. Remove the temporary seed URL afterward. Keep the encryption key private. Future cache loss stops scheduled acquisition rather than recreating live forecasts from current predictions.
4. Confirm the next eligible run, its protected Engine checks, the deployed publication marker, and the subsequent zero-cost pregame check. The workflow only stages the bounded public display files when validation succeeds. Raw inputs, normalized seasons, source checkpoints and forecast ledgers are never committed. After a bot push it dispatches Engine checks and verifies the run's exact commit. If football advanced main during dispatch, the checked descendant must contain the identical basketball manifest. Render separately checks the exact commit it builds. If the protected checks fail, fix the failure and retry the release through the existing exact-revision gate. A different deployed marker means the previous publication is still live. [GitHub dispatch API](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event) · [Render deploy behavior](https://render.com/docs/deploys)
5. For rollback, turn off `BASKETBALL_REFRESH_ENABLED` and keep the sealed cache intact. Use the existing protected Render rollback/revert to the previous exact checked site revision. Restore a separately verified encrypted seed if the runner cache is lost. Actions caches may expire or be evicted, so the protected backup matters. [GitHub cache rules](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)

As written, this worktree leaves production automation disabled. The actual credential binding, hosted cache seed, scheduled execution, and subsequent guarded deployment require production verification. Eighteen targeted tests passed. The offline replay authenticated and restored the six-season seed, replayed five captured endpoint responses to build 2,250 validated display files, preserved that publication on an identical refresh, and retained its manifest after a simulated provider 503. The replay spent zero provider calls.
